# Direct phone study cameras

Signed-in students can select Pair another phone or browser in the shared Camera source menu, enable the optional check-in and open its private link on another device signed into the same account. Tapping Connect on that device explicitly allows video sharing. Audio is off. The receiving study browser runs the existing on-device analysis, with the same timer, cumulative summaries and self-view. Choosing a source alone does not open a camera.

Video uses a direct WebRTC connection with no configured STUN/TURN or media server. This slice requires devices on the same network and does not promise every LAN, VLAN, VPN, firewall or browser combination. The phone chooses its front/back camera. For browser-visible USB, capture and virtual cameras the existing picker remains available. Direct IP/WHEP, RTSP/ONVIF gateways and physical hardware validation remain open.

Both ends may stop sharing. Pause, cancellation, source changes, policy failures and leaving the phone page stop capture; the ordinary study timer continues independently. Phone visibility changes also stop sharing. A new invitation opened in an existing tab replaces the old one, including same-document fragment navigation. Stale streams and late permissions cannot revive stopped capture. Remote failures clear the global active-camera reference, preview and detached video element.

The public phone page has only first-party scripts/CSS, no analytics, no service-worker registration, no-referrer/no-store headers and frame protection. The invitation secret lives in the URL fragment, is removed from visible history after parsing, and is never sent as a query/path parameter. An invitation is single-use and cannot be claimed after its immutable120-second setup deadline. Each role has a separate high-entropy key, stored only as a hash. Both devices must authenticate as the owner; a link alone grants no access. One pairing per owner and a user-row lock serialize replacement.

Connection details contain network metadata and therefore use required encryption at rest. Missing or invalid encryption fails closed. The API accepts bounded video-only SDP, rejects audio/data channels and replacement negotiation, checks fresh owner/school permission after lock waits and before returning signaling data, and reads expiry time after locking. Thirty-second device leases and a two-hour absolute limit bound use. SDP is cleared once connected. Physical deletion after abandonment occurs on a successful maintenance batch: up to500 expired/stale rows per run, ordered and skip-locked. The existing notification ticker and authenticated notification cron run this purge; /cron/study-cameras offers a cleanup-only authenticated path. A failed maintenance scheduler, a backlog and backup retention are separate limits; logical expiry does not assert immediate physical backup deletion. Account deletion explicitly covers the new table. Polling has a separate bounded per-account rate limit.
