# Course generator technical report

## Resource discovery and licensing

`catalog.py` contains reviewed metadata with original URL, provider, topic keywords, license URL and check date. Python foundations uses PSF tutorial links and Harvard CS50 Python week pages, ordered in six lessons/two units. Elementary algebra uses six topic-matched OpenStax section links and Khan Academy practice, progressing from variables and equations to coordinates and slope in two units. Subject filtering prevents programming resources from being selected for algebra. MIT linear algebra metadata is available for matching but does not make arbitrary curated math courses work. Topic matching is literal and bounded, not embedding retrieval or a web crawler. Unsupported curated topics return a clear validation error.

Resources are source links. Course text, videos and transcripts are not copied, cached or rehosted. Harvard's material has noncommercial/share-alike conditions; MIT's terms also require attention before redistribution. Linking does not establish permission for later scraping, embedding or commercial reuse. OpenStax's current elementary-algebra terms also include noncommercial/share-alike conditions; its use here is links only. Review [OpenStax preface and terms](https://openstax.org/books/elementary-algebra-2e/pages/preface), [Khan terms](https://www.khanacademy.org/about/tos), [PSF license](https://docs.python.org/3/license.html), [CS50 license](https://cs50.harvard.edu/python/license/) and [MIT terms](https://ocw.mit.edu/pages/privacy-and-terms-of-use/) before expanding ingestion.

## Original generation and validation

An administrator confirms provider use for both the blueprint and lesson job. The blueprint call receives the supplied goal. Lesson calls receive the lesson specification and saved request preferences; account profile and student records are not automatically attached. The blueprint includes title, overview, outcomes, prerequisites, units and sequenced lesson objectives/time. Validation accepts1–24 lessons and permits only earlier lesson keys as dependencies. Outline edits are allowed before generation begins. Request details are bounded, inspectable and editable; they describe stated preferences, not verified knowledge. See [course request details](15-course-request-details.md). Generation accuracy and educational/time feasibility remain unverified.

Original lessons require explanation, worked example, independent practice prompt, common mistakes, delayed review and a multiple-choice knowledge check with answer explanation. Field lengths, distinct options and answer indices are validated. Extra provider resource/link fields are discarded. The five teaching sections render sanitized Markdown, math, tables and explicitly tagged code blocks; generated HTML, links and images remain inert. Quiz text and outline text remain plain text. See [content rendering](13-content-rendering.md) for bounds, dependency licenses and adversarial browser evidence. This validates structure, not factual accuracy, curriculum alignment or age suitability. A human must inspect each lesson and key before scoring is unlocked. The current confirmation is an owner-admin attestation, not an independent teacher approval workflow.

Real provider generation is **blocked in this environment** by existing Gemini contractual approval/Vertex configuration requirements. Fixture-backed generation, validation, persistence, review and scoring pass. No provider-quality benchmark has been completed.

## Storage and jobs

Courses, blueprints, generated lesson checkpoints and jobs persist in additive SQLAlchemy tables. Run `python -m flask --app App learning-worker --steps 25` in the correctly configured application environment. This processes a bounded batch; repeated scheduling/supervision is an operator responsibility. Browser refresh reads saved progress and does not generate content.

Completed original courses now support individual lesson editing and regeneration through a preserved course revision. Editing validates the five teaching fields and knowledge-check fields. Regeneration copies the other lessons and queues exactly the missing lesson through the existing bounded worker. Both preserve the original course and its scored evidence, create new lesson IDs, and require fresh human review; copied items never become independent evidence. Display, review and export order follow the blueprint rather than insertion order. See [lesson revisions](14-lesson-revisions.md). Curated-source edits, fresh assessment variants and module restructuring after generation remain outside this change.

States include queued/running/completed/failed/cancelled; completed jobs leave the course needing human review. Each lease lasts ten minutes. A worker saves one lesson, then requeues the job; one extra step marks completion. Failed/cancelled jobs can retry without discarding completed lessons. Retries preserve token reservations. Maximum48 lesson attempts prevents unbounded retry spending. Lowered policy budgets can cause retries to remain blocked; the UI preserves partial lessons and shows the failure class. Error classes are intentionally concise; a richer operator diagnostic interface is remaining work.

## Cost and adaptation

Each blueprint request permits one model attempt with4000 output tokens and is rate-limited10 requests/hour. Each generated lesson permits one model attempt with2500 output tokens; conservative input-byte reservations plus output ceilings are persisted before spending. Failed attempts retain their reservation. The default effective lesson-job ceiling is24000 tokens; organizations can restrict it further. The blueprint is a **separate** bounded call outside that lesson-job budget. A monthly ledger now reserves blueprint and original-lesson tokens against every applicable school/district counter (default100000; each organization may set its own ceiling). Counters use atomic conditional increments; a child's smaller allowance cannot reduce its siblings' shared district ceiling. Individual accounts without an organization have an account-scoped counter. Failures keep reservations. There is no accurate currency-price ledger or provider invoice reconciliation; restored PostgreSQL concurrent proof remains pending. The existing provider's account allowance continues to apply where configured.

Recommendations deterministically find missing or failed/assisted prerequisites and suggest different practice; delayed review suggestions are limited to recent evidence. Builders can see answer keys, so their attempts never qualify as independent mastery. The optional reviewed-practice preview now obtains fresh items and remediation from the existing scored practice path, and its outcomes appear in the hub and consent-gated tutor context. Fresh course-specific assessment generation, error taxonomies and educational outcome validation remain incomplete.

## Access, video and future rollout

All course APIs require authenticated administrator eligibility, institution permission, beta permission and explicit `school_course_generator` flag. Ordinary/Premium users cannot bypass these checks. Courses are owner-only: another school admin cannot automatically read a builder's course. Course sharing is not implemented.

Existing educational videos are reached through original CS50 source-page links. No video is generated or stored. The internal-alpha video capability always denies with provider-not-integrated, even if its flag is switched on. The future `premium` entitlement is registry metadata only; there is no current Premium course rollout or billing promise. A future launch needs provider approval, stronger review, eligibility/consent, quotas, current price estimation, accessibility, monitoring and live validation before changing the admin gate.
